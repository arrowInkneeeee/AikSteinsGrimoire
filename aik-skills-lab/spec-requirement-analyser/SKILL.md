# spec-requirement-analyser

## 职责

1. 协调各个技能的执行顺序
2. 管理人机协作节点
3. 整合各技能输出为 PRD 文档
4. 确保需求分析流程完整执行

## 执行流程

```
┌─────────────────────────────────────────────────────────────┐
│  1. 接收原始需求输入（会议记录、聊天记录、口头描述等）          │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  2. 调用 requirement-extractor                              │
│     → 提取结构化功能点列表                                   │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  3. 调用 requirement-clarifier                              │
│     → 识别模糊点，生成澄清问题                               │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  4. 【人机协作节点】                                          │
│     → 向用户展示澄清问题                                      │
│     → 收集用户回答                                           │
│     → 更新功能点列表                                         │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  5. 调用 conflict-detector                                  │
│     → 检查需求冲突和重复                                     │
│     → 生成冲突报告                                           │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  6. 【人机协作节点】（如存在 high severity 冲突）              │
│     → 向用户展示冲突报告                                     │
│     → 协助用户解决冲突                                       │
│     → 更新功能点列表                                         │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  7. 调用 user-story-generator                               │
│     → 生成标准格式用户故事                                   │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  8. 调用 acceptance-criteria-writer                         │
│     → 编写 Gherkin 格式验收标准                              │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  9. 调用 feasibility-checker                                │
│     → 评估技术可行性                                         │
│     → 识别风险和依赖                                         │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  10. 调用 priority-assessor                                 │
│     → 评估需求优先级 (MoSCoW)                                │
│     → 生成推荐实施序列                                       │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  11. 整合输出为 PRD 文档                                     │
│     → 生成结构化产品需求文档                                 │
└─────────────────────────────────────────────────────────────┘
```

## 调用的技能

| 顺序 | 技能名称 | 用途 | 是否必须 |
|------|---------|------|---------|
| 1 | requirement-extractor | 提取功能点 | 是 |
| 2 | requirement-clarifier | 澄清模糊需求 | 是 |
| 3 | conflict-detector | 检测冲突 | 是 |
| 4 | user-story-generator | 生成用户故事 | 是 |
| 5 | acceptance-criteria-writer | 编写验收标准 | 是 |
| 6 | feasibility-checker | 可行性评估 | 是 |
| 7 | priority-assessor | 优先级排序 | 是 |

## 人机协作节点

### 节点 1：需求澄清

**触发条件**: requirement-clarifier 生成澄清问题后

**执行动作**:
1. 以清晰的格式展示所有澄清问题
2. 为每个问题提供建议选项（如适用）
3. 收集用户回答
4. 根据回答更新功能点列表

**输出示例**:
```
需要您澄清以下问题：

[Q1] 关于 "快速浏览" 的性能要求：
    建议选项：
    [ ] 页面加载时间 < 2秒
    [ ] 页面加载时间 < 3秒  
    [ ] 首屏渲染 < 1秒
    [ ] 其他：________

[Q2] 关于支付方式：
    建议选项：
    [ ] 仅微信和支付宝
    [ ] 增加银联支付
    [ ] 后续再扩展
```

### 节点 2：冲突解决

**触发条件**: conflict-detector 发现 high severity 冲突

**执行动作**:
1. 展示冲突报告
2. 提供解决建议
3. 协助用户做出决策
4. 更新功能点列表

**输出示例**:
```
检测到以下需要解决的冲突：

[严重] 逻辑冲突：F001 vs F002
    问题：F001 要求所有商品对所有用户可见，F002 要求 VIP 商品仅 VIP 可见
    建议解决方案：
    [ ] 采用方案 A：所有商品公开，VIP 享受折扣而非专属商品
    [ ] 采用方案 B：支持 VIP 专属商品，普通商品公开
    [ ] 采用方案 C：混合模式，部分商品专属，部分公开
```

## 使用示例

### 启动命令

```
请帮我分析以下需求：

[粘贴会议记录、聊天记录或需求描述]
```

### 完整执行示例

**用户输入**:
```
我们需要开发一个在线学习平台。学生可以观看视频课程，
老师可以上传课程。还要支持在线测验功能。
```

**执行流程**:

1. **requirement-extractor** 提取功能点
   - F001: 学生观看视频课程
   - F002: 老师上传课程
   - F003: 在线测验功能

2. **requirement-clarifier** 识别模糊点
   - Q1: "视频课程"的格式支持？
   - Q2: "在线测验"的题型？
   - Q3: 用户认证方式？

3. **【人机协作】** 用户回答澄清问题

4. **conflict-detector** 检查冲突
   - 无冲突

5. **user-story-generator** 生成用户故事
   - US-001: 作为学生，我想观看视频课程...
   - US-002: 作为老师，我想上传课程...
   - US-003: 作为学生，我想参加在线测验...

6. **acceptance-criteria-writer** 编写验收标准
   - 为每个用户故事编写 Gherkin 场景

7. **feasibility-checker** 评估可行性
   - 视频播放：可行，需考虑存储和 CDN
   - 测验功能：可行，需设计题库系统

8. **priority-assessor** 评估优先级
   - Must: US-001, US-002
   - Should: US-003

9. **生成 PRD 文档**
   - 整合所有输出为结构化文档

## 注意事项

- 确保每个技能输出质量后再进入下一步
- 人机协作节点要清晰展示问题和选项
- 保留所有中间输出便于追溯
- PRD 文档应导出为 Markdown 格式保存
- 支持增量更新（需求变更时）
