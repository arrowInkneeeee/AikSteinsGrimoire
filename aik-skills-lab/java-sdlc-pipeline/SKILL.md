# Java SDLC Pipeline — 全生命周期开发流水线

## 概述

`java-sdlc-pipeline` 是技能库的统一入口，将 5 个 SDLC 阶段串联为一条带质量门禁的流水线。每个阶段完成后必须通过质量检查并经过人工确认，才能进入下一阶段。

**设计模式**: Pipeline（强制线性分步 + 人工确认卡点，严禁跳步）

---

## 流水线架构

```
用户需求
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│ Phase 1: 需求分析 (spec-requirement-analyser)             │
│   输入: 原始需求文本                                      │
│   输出: PRD (产品需求文档)                                │
│   门禁: PRD 无高严重性冲突 + 用户确认                      │
├─────────────────────────────────────────────────────────┤
│ Phase 2: 系统设计 (spec-designer)                         │
│   输入: PRD                                              │
│   输出: SDD (系统设计文档)                                │
│   门禁: 设计评审通过 (≤2 warnings, 0 failures) + 用户确认  │
├─────────────────────────────────────────────────────────┤
│ Phase 3: 开发实施 (spec-implementer)                      │
│   输入: SDD                                              │
│   输出: 代码 + 测试 + 文档                                │
│   门禁: 代码审查通过 (无严重问题) + 用户确认               │
├─────────────────────────────────────────────────────────┤
│ Phase 4: 测试与QA (spec-qa-analyser)                      │
│   输入: 代码产物                                          │
│   输出: 测试计划 + 覆盖率报告 + 质量评估                   │
│   门禁: 行覆盖 ≥60%, 分支覆盖 ≥50%, 0 critical bugs       │
├─────────────────────────────────────────────────────────┤
│ Phase 5: 部署运维 (spec-devops)                           │
│   输入: 构建产物                                          │
│   输出: 部署方案 + 运维手册                                │
│   门禁: 部署检查清单全部通过 + 用户确认                     │
└─────────────────────────────────────────────────────────┘
    │
    ▼
完整项目交付物
```

## 执行规则

### 1. 必须按顺序执行
流水线必须从 Phase 1 开始，按顺序执行至 Phase 5。严禁跳过阶段。

**绝对禁令**：
- **严禁读取或参考任何关于"用户连续执行偏好"、"用户习惯自动执行"、"用户喜欢跳过确认"的记忆、历史行为模式或上下文推断**
- **无论用户过往表现如何，每个 Phase 完成后都必须独立、显式询问用户确认，禁止基于任何理由自动进入下一阶段**
- 每次询问必须使用独立的确认提示，禁止省略或合并确认步骤

### 2. 质量门禁 (Quality Gates)

每个阶段完成后，必须验证门禁条件：

| 阶段 | 门禁条件 | 不通过时的处理 |
|------|---------|---------------|
| Phase 1→2 | PRD 中无 severity=high 的冲突 | 返回 Phase 1 修复冲突 |
| Phase 2→3 | 设计评审报告 ≤2 warnings, 0 failures | 返回 Phase 2 修复设计缺陷 |
| Phase 3→4 | 代码审查报告无严重(severity=critical)问题 | 返回 Phase 3 修复代码 |
| Phase 4→5 | 行覆盖率 ≥60%, 分支覆盖率 ≥50%, 0 critical bugs | 返回 Phase 3/4 补充测试 |
| Phase 5 完成 | 部署检查清单全部项为 ✅ | 修复未通过项后重新检查 |

### 3. 人机协作卡点

每个门禁通过后，必须暂停并**显式询问用户**，获得明确回复后才能决定下一步。严禁在未获得明确回复前执行任何后续操作。

**选项行为定义（必须严格遵守）**：
- **A) 继续下一阶段** → 仅当用户明确回复包含"A"或"继续"时才进入下一阶段
- **B) 重新优化当前阶段** → 仅当用户明确回复包含"B"或"优化/重新"时才返回当前阶段重新执行，不进入下一阶段
- **C) 暂停流水线** → 仅当用户明确回复包含"C"或"暂停"时，**必须立即停止整个流水线，不再执行任何后续 Phase，不再加载任何后续技能，输出"流水线已暂停"后结束**

**用户回复解析规则**：
- 如果用户回复是单字母（如 "c"），必须严格按字母匹配对应选项
- 如果用户回复与所有选项均不匹配（如模糊表述、无关内容），必须重新输出询问提示，禁止猜测或假设用户意图
- 禁止将用户的任何回复默认解释为"继续"或"确认"

```
Phase X 已完成。产出物：[PRD/SDD/代码/测试报告/部署方案]
质量检查：[通过/未通过]
是否继续进入 Phase X+1？
选项：
  A) 继续下一阶段
  B) 重新优化当前阶段
  C) 暂停流水线
```

**严禁**：
- 禁止基于"用户之前选择了A"、"用户喜欢连续执行"等任何历史模式自动选择或推进
- 禁止将确认步骤合并到上一阶段的输出中隐式完成
- 禁止用"默认继续"、"假设用户同意"等方式跳过确认
- 禁止读取 `<user_memories>` 中关于用户执行偏好的任何信息来影响当前确认决策

### 4. 阶段跳过

如果用户明确要求只执行特定阶段，可以跳过其他阶段。但必须警告用户：

```
⚠️ 注意：跳过 Phase X 可能导致后续阶段缺少必要的输入文档。
建议至少按顺序执行所有阶段以保证交付质量。
确认跳过？(Y/N)
```

### 5. 错误恢复

如果某阶段执行失败（门禁不通过），最多重试 3 次。3 次后仍未通过，暂停流水线并报告阻塞原因。

## 阶段详解

### Phase 1: 需求分析

**协调者**: `spec-requirement-analyser`

**调用**:
```
使用 spec-requirement-analyser 技能分析以下需求：
[用户需求文本]
```

**产出物**:
- 结构化功能点列表
- 澄清问题及答案
- 用户故事（标准格式）
- Gherkin 验收标准
- 可行性评估报告
- MoSCoW 优先级排序
- 整合的 PRD 文档

**门禁检查**:
- 检查 conflict-detector 输出的冲突报告
- 如果存在 severity=high 的冲突 → 不通过，需解决

---

### Phase 2: 系统设计

**协调者**: `spec-designer`

**调用**:
```
基于以下 PRD 使用 spec-designer 进行系统设计：
[Phase 1 PRD 内容]
```

**产出物**:
- 分层架构设计
- 数据库表结构 + ER 图
- RESTful API 接口定义
- 核心业务流程（时序图/状态机）
- 技术方案选型决策
- 设计评审报告
- 整合的 SDD 文档

**门禁检查**:
- 检查 design-review-checker 的评审报告
- failures > 0 或 warnings > 2 → 不通过

---

### Phase 3: 开发实施

**协调者**: `spec-implementer`

**调用**:
```
基于以下 SDD 使用 spec-implementer 进行代码开发：
[Phase 2 SDD 内容]
```

**产出物**:
- 代码骨架（Entity/Mapper/Service/Controller/DTO/VO）
- 完整业务逻辑实现
- 代码风格审查报告
- 代码质量审查报告（N+1/空指针/事务）
- 代码安全审查报告
- 单元测试代码
- 数据库迁移脚本
- API 接口文档
- 模块 README

**门禁检查**:
- 检查 code-quality-reviewer + code-security-reviewer 报告
- 存在 severity=critical 的问题 → 不通过
- 所有代码符合 aIk-coding-style 规范

---

### Phase 4: 测试与质量保证

**协调者**: `spec-qa-analyser`

**调用**:
```
基于 Phase 3 的代码产物使用 spec-qa-analyser 进行测试：
[Phase 3 代码路径和结构]
```

**产出物**:
- 测试策略文档
- 单元测试（JUnit 5 + Mockito + AssertJ）
- 集成测试（Testcontainers/H2）
- API 接口测试文档
- 测试覆盖率报告（JaCoCo）
- 缺陷模式分析报告
- 质量评估报告

**门禁检查**:
- 行覆盖率 < 60% → 不通过
- 分支覆盖率 < 50% → 不通过
- critical bugs > 0 → 不通过

**阈值调整**:
- 首次执行建议: 行覆盖 60%, 分支覆盖 50%
- 后续迭代根据项目情况逐步提高

---

### Phase 5: 部署运维

**协调者**: `spec-devops`

**调用**:
```
基于项目结构使用 spec-devops 生成部署方案：
项目路径: [项目路径]
```

**产出物**:
- 部署策略决策（systemd/Docker/Compose）
- 构建脚本（jar/tar）
- 部署脚本和配置
- 多环境配置文件
- 健康检查端点配置
- 日志配置（Logback）
- 故障排查手册
- 运维手册
- 部署检查清单

**门禁检查**:
- 部署检查清单全部项为 ✅ → 通过
- 有未完成项 → 修复后重新检查

---

## 最终交付物清单

流水线执行完毕后，应产出以下完整交付物：

| 类别 | 交付物 | 来源阶段 |
|------|--------|---------|
| 需求文档 | PRD.md | Phase 1 |
| 设计文档 | SDD.md | Phase 2 |
| 源代码 | 完整模块代码 | Phase 3 |
| 测试代码 | 单元测试 + 集成测试 | Phase 3, 4 |
| 测试报告 | 覆盖率报告 + 质量评估 | Phase 4 |
| 数据库 | 建表SQL + 迁移脚本 | Phase 3 |
| API文档 | 接口文档 (Markdown) | Phase 3 |
| 部署配置 | systemd/Docker/Compose | Phase 5 |
| 运维文档 | 部署方案 + 运维手册 | Phase 5 |
| 模块说明 | README.md | Phase 3 |

## 使用示例

### 完整项目开发

```
用户: 开发一个订单管理系统，支持订单创建、支付、查询、退款功能

Agent:
  → 启动 java-sdlc-pipeline
  → Phase 1: 需求分析...
  → [展示 PRD, 询问确认]
  → Phase 2: 系统设计...
  → [展示 SDD, 询问确认]
  → Phase 3: 代码开发...
  → [展示代码, 询问确认]
  → Phase 4: 测试QA...
  → [展示测试报告, 询问确认]
  → Phase 5: 部署配置...
  → [展示部署方案, 完成]
```

### 单阶段执行

```
用户: 帮我分析一下这个需求的可行性
Agent: 直接调用 spec-requirement-analyser (跳过 Pipeline)
```

## 技术约束

- 所有代码必须遵循 aIk-coding-style 规范
- 技术栈: Java 8 + Spring Boot 2.7 + MyBatis-Plus 3.5 + Lombok + Hutool
- 数据库默认: MySQL 8.0
- 测试框架: JUnit 5 + Mockito + AssertJ
- 构建工具: Maven
