# requirement-engineering

需求工程全流程技能，覆盖功能点提取、需求澄清、冲突检测、用户故事生成、可行性评估、优先级排序，最终产出结构化PRD文档。

## 子命令

### extract

从非结构化文本（会议记录、聊天日志、口头描述等）中提取结构化功能点列表。

**触发条件**：用户提供原始需求文本，要求提取功能点

**输入**：
- 非结构化需求文本（会议记录、聊天日志、口头描述等）

**输出**：
- 结构化功能点列表，格式：`F001: [功能描述] | 类别: core/enhancement/optional | 状态: 待澄清`

**执行步骤**：
1. 阅读原始文本，识别所有涉及的功能需求
2. 去除重复表述，合并同义描述
3. 为每个功能点分配唯一ID（F001, F002...）
4. 标注功能类别（core/enhancement/optional）
5. 输出结构化功能点列表

---

### clarify

识别功能点中的模糊、不完整之处，生成针对性澄清问题。

**触发条件**：功能点列表已产出，需要识别模糊点

**输入**：
- 结构化功能点列表（来自 extract 子命令）

**输出**：
- 澄清问题列表，每个问题附带建议选项

**执行步骤**：
1. 逐个审查功能点，识别以下模糊类型：
   - 性能要求不明确（如"快速"、"大量"）
   - 业务规则不完整（如边界条件、异常处理）
   - 用户角色未明确
   - 数据范围未定义
2. 为每个模糊点生成澄清问题
3. 为每个问题提供 2-3 个建议选项
4. 输出澄清问题列表

**人机协作节点**：
- 展示澄清问题及建议选项
- 收集用户回答
- 根据回答更新功能点列表

---

### conflict-check

检测功能点之间的矛盾、重复或依赖缺失。

**触发条件**：功能点已澄清，需要检查一致性

**输入**：
- 已澄清的功能点列表

**输出**：
- 冲突报告（JSON格式），包含冲突类型、严重度、涉及功能点、解决建议

**执行步骤**：
1. 加载 `references/conflict-checklist.md` 中的4种冲突类型定义
2. 逐对检查功能点，检测以下冲突：
   - **逻辑冲突**：两个功能点互相矛盾
   - **重复需求**：两个功能点实质相同
   - **依赖缺失**：功能A依赖功能B但B未列出
   - **范围冲突**：功能点超出项目边界
3. 对语义相似度 >80% 的功能点对标记为疑似重复
4. 为每个冲突标注严重度（high/medium/low）
5. 输出冲突报告

**人机协作节点**（如存在 high 严重度冲突）：
- 展示冲突报告
- 提供解决建议（方案A/B/C）
- 协助用户做出决策
- 更新功能点列表

### user-story

将功能点转化为标准用户故事格式，并编写Gherkin验收标准。

**触发条件**：功能点已澄清且无高严重度冲突

**输入**：
- 已澄清的功能点列表

**输出**：
- 标准用户故事列表（As a... I want... So that...）
- 每个用户故事附带Gherkin格式验收标准

**执行步骤**：
1. 为每个功能点生成用户故事：
   - 识别用户角色（As a...）
   - 明确功能需求（I want...）
   - 阐述业务价值（So that...）
2. 为每个用户故事编写验收标准：
   - 使用Gherkin格式（Given-When-Then）
   - 覆盖正常流程、异常流程、边界条件
3. 按MoSCoW初步分类（Must/Should/Could/Won't）
4. 输出用户故事列表

---

### feasibility

评估用户故事的技术可行性、复杂度和风险。

**触发条件**：用户故事已生成，需要评估可行性

**输入**：
- 用户故事列表
- 项目技术栈信息（从pom.xml或用户指定）

**输出**：
- 可行性评估报告，包含：可行/部分可行/不可行、复杂度（低/中/高）、风险等级、预估工期、替代方案建议

**执行步骤**：
1. 加载 `references/java-feasibility-dimensions.md` 中的8维评估标准
2. 逐故事评估以下维度：
   - 分层适配性、MyBatis-Plus适用性、Stream API适用性
   - SQL复杂度、事务边界、空指针风险、性能风险、日志规范
3. 综合判定复杂度（低/中/高）
4. 识别风险点并给出缓解措施
5. 预估工期（人天）
6. 对不可行或部分可行的故事给出替代方案
7. 输出可行性评估报告

---

### prioritize

使用MoSCoW方法对用户故事进行优先级排序。

**触发条件**：用户故事已通过可行性评估

**输入**：
- 用户故事列表（含可行性评估结果）

**输出**：
- MoSCoW分类结果（Must/Should/Could/Won't）
- 推荐实施序列

**执行步骤**：
1. 加载 `references/moscow-decision-matrix.md` 中的权重矩阵
2. 为每个用户故事评分（4维加权）：
   - 业务价值（权重40%）
   - 用户影响（权重30%）
   - 技术依赖（权重20%）
   - 实现成本（权重10%，反向计分）
3. 根据优先级决策矩阵判定MoSCoW分类
4. 生成推荐实施序列（Phase 1/2/3）
5. 输出优先级排序结果

---

### full

完整需求分析流程，从原始文本到结构化PRD文档。

**触发条件**：用户说"分析需求"、"写PRD"、"整理需求"等全流程场景

**输入**：
- 原始需求文本
- 项目技术栈信息（可选，用于可行性评估）

**输出**：
- 结构化PRD文档（Markdown格式），保存至 `docs/prd/` 目录

**执行步骤**：
1. 执行 `extract` → 产出功能点列表
2. 执行 `clarify` → 识别模糊点
3. **【人机协作】** 展示澄清问题，收集用户回答
4. 执行 `conflict-check` → 检测冲突
5. **【人机协作】**（如有high严重度冲突）展示冲突报告，协助解决
6. 执行 `user-story` → 生成用户故事 + 验收标准
7. 执行 `feasibility` → 评估可行性
8. 执行 `prioritize` → 优先级排序
9. 整合所有输出为PRD文档（使用 `assets/prd-template.md` 模板）
10. 保存PRD文档至 `docs/prd/` 目录

**质量门禁**：
- PRD中无 high 严重度冲突
- 所有用户故事均有验收标准
- 可行性评估覆盖所有用户故事

## 输入契约

| 输入项 | 路径/来源 | 必须 | 降级策略 |
|--------|----------|------|---------|
| 原始需求文本 | 用户输入 | 是 | 无 |
| 项目技术栈 | pom.xml 或用户指定 | 否（feasibility子命令需要） | 默认 Java 8 + Spring Boot + MyBatis-Plus + MySQL |

## 输出契约

| 输出项 | 路径 | 格式 |
|--------|------|------|
| PRD文档 | `docs/prd/prd-{项目名}-v{版本}.md` | Markdown，遵循 `assets/prd-template.md` |
| 冲突报告 | 内联输出（full流程中不单独保存） | JSON |
| 可行性评估 | 内联输出（full流程中不单独保存） | 表格 |

## 工作流上下文

**上游技能**：无（本技能为流程起点）

**下游技能**：
- `system-design`：消费PRD文档，产出SDD
- `code-implementation`：消费PRD中的用户故事和验收标准

## 质量门禁

| 检查点 | 条件 | 动作 |
|--------|------|------|
| 澄清完成 | 所有模糊点已回答 | 继续 |
| 冲突解决 | 无 high 严重度冲突 | 继续，否则暂停等待用户解决 |
| PRD完整性 | 包含6节完整结构 | 继续 |

## 约束

- 所有代码产出必须遵循 `aIk-coding-style` 规范
- PRD文档使用 Markdown 格式
- 用户故事使用标准格式（As a... I want... So that...）
- 验收标准使用 Gherkin 格式（Given-When-Then）
- 优先级排序使用 MoSCoW 方法
