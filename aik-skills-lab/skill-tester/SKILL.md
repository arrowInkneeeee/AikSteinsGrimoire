# Skill Tester — 技能质量测试框架

## 概述

`skill-tester` 将 TDD（测试驱动开发）理念引入技能开发。通过系统的 RED → GREEN → REFACTOR 循环，确保每个技能不仅"写得好"，更"起作用"。

**设计模式**: Reviewer（测试技能的质量，而非测试代码）

---

## RED-GREEN-REFACTOR 方法论

```
┌─────────────────────────────────────────────────────┐
│ RED: 暴露模型违规                                     │
│   在没有技能的情况下执行目标任务                        │
│   记录模型违反了多少条规则                              │
│   量化：违规类型 × 违规次数                            │
├─────────────────────────────────────────────────────┤
│ GREEN: 最小化拦截                                    │
│   加载技能的最小化指令版本                             │
│   重新执行相同的目标任务                               │
│   验证：违规是否被阻止？                               │
│   如果未阻止 → 增强指令后重试                          │
├─────────────────────────────────────────────────────┤
│ REFACTOR: 持续收紧                                   │
│   识别模型的"合理化推脱路径"                           │
│   添加防护规则，避免过拟合到单一场景                    │
│   回退测试：用之前的违规场景进行回归                    │
│   记录：变更内容 + 效果对比数据                        │
└─────────────────────────────────────────────────────┘
```

## 四类测试策略

根据技能类型选择对应的测试方法：

| 类型 | 测试方法 | 适用技能 |
|------|---------|---------|
| **纪律型** | 时间 + 疲劳双重施压，验证服从性 | code-style-reviewer, aIk-coding-style |
| **技术型** | 新场景迁移能力测试 | code-generator, api-designer, database-designer |
| **思维型** | 评估模式适用边界 | tech-solution-selector, architecture-designer |
| **资料型** | 信息检索与落地准确度 | api-doc-generator, troubleshooting-guide |

## 测试执行流程

### 步骤 1: 定义测试目标

```
技能名称: code-style-reviewer
测试目标: 验证代码风格规范是否被有效执行
测试场景: 5 个（含正确代码和违规代码）
```

### 步骤 2: RED 阶段 —— 建立基线

```bash
# 不加载 code-style-reviewer 技能
# 让模型审查以下代码片段
```

**测试用例 1: 错误类注释格式**
```java
// 缺少 -anchor 标记
/**
 * 订单服务
 */
public class OrderService { }
```

**预期违规**:
- [ ] 类注释缺少 `-anchor` 标记
- [ ] `@author` 不是 `a I k .`
- [ ] 缺少 `@implNote JDK 8`

**记录结果**:
```
RED 阶段结果:
- 测试用例数: 5
- 违规发现率: 20% (模型仅检测到 1/5 违规)
- 漏检率: 80%
```

### 步骤 3: GREEN 阶段 —— 验证阻止

```bash
# 加载 code-style-reviewer 技能
# 重新审查相同代码片段
```

**验证标准**:
```
GREEN 阶段结果:
- 违规检测率应 > 90%
- 误报率应 < 10%
- 实际问题归因准确率 > 80%
```

### 步骤 4: REFACTOR 阶段 —— 持续改进

```bash
# 分析 GREEN 阶段漏检的违规
# 收紧技能指令中的对应规则
# 回归测试所有之前的测试用例
```

## 测试报告模板

每次测试生成结构化报告：

```markdown
## 技能测试报告: {技能名称}

### 测试信息
- 测试日期: {date}
- 测试者: {tester}
- 技能版本: {version}

### RED 阶段基线
| 测试用例 | 违规类型 | 是否检测到 | 说明 |
|---------|---------|-----------|------|
| TC-01 | 类注释格式 | ❌ | 未检测到 -anchor 缺失 |
| TC-02 | 命名规范 | ✅ | 正确检测 |
| ... | ... | ... | ... |

### GREEN 阶段验证
| 测试用例 | RED检测 | GREEN检测 | 改进 |
|---------|---------|----------|------|
| TC-01 | ❌ | ✅ | 技能已修正 |
| ... | ... | ... | ... |

### REFACTOR 改进项
1. **问题**: 对空注释块未检测
   **改进**: 添加空注释检查规则
   **效果**: 误报率从 15% 降至 5%

### 质量指标对比
| 指标 | RED基线 | GREEN目标 | 实际 |
|------|---------|----------|------|
| 违规检测率 | 20% | >90% | 95% |
| 误报率 | 8% | <10% | 5% |
| 归因准确率 | 50% | >80% | 85% |
```

## 双人迭代模式

推荐分工：
- **技能设计者**: 编写技能指令，设计测试场景
- **技能测试者**: 执行 RED → GREEN → REFACTOR 循环，独立验证

**为什么分开？**
- 设计者对自己的指令有认知盲区
- 独立测试者能从"模型会怎么误解"的角度思考
- 避免"我写的肯定没问题"的确认偏差
