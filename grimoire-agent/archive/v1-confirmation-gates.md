# 03 — 确认门禁策略

> Agent 在流水线中如何决定"自己做"还是"问你"

## 核心矛盾

`java-sdlc-pipeline` 技能明确规定：

> "无论用户过往表现如何，每个 Phase 完成后都必须独立、显式询问用户确认，禁止基于任何理由自动进入下一阶段"

这是 Skill 层面的硬规则。但如果 Agent 严格照搬，每个阶段都暂停，Agent 就退化成了"需要你时刻盯着的高级脚本"——**违背了创建 Agent 的初衷**。

### 解决思路

Agent **不直接调用** `java-sdlc-pipeline` Skill，而是：

- 用自己的判断逻辑**直接编排**各阶段的 spec-* 协调者
- 用"三级自主权模型"替代 Skill 的硬确认规则
- `java-sdlc-pipeline` 保留给"手动模式下用户直接调用 Skill"的场景

```
用户直接调用 java-sdlc-pipeline → 严格每阶段确认（Skill 原规则）
用户通过 aik-dev-agent        → 三级自主权模型（Agent 判断）
```

## 三级自主权模型

```
┌─────────────────────────────────────────────────┐
│                                                  │
│  🟢 绿灯级（Agent 自主决策 + 事后告知）             │
│  ├─ 命名规范 / 代码格式化                          │
│  ├─ 注释风格（anchor / note）                      │
│  ├─ 单方法实现细节                                │
│  ├─ 测试用例构造                                  │
│  ├─ 已有模式的复用                                │
│  ├─ 代码审查 → 风格/格式类问题自动修复              │
│  └─ 在摘要中标注所有绿灯决策                       │
│                                                  │
│  🟡 黄灯级（Agent 决策 + 摘要报告 + 等待确认）       │
│  ├─ 模块/类的设计方案                              │
│  ├─ API 接口参数设计                              │
│  ├─ 数据库查询策略选择（Lambda vs XML）            │
│  ├─ 代码审查 → 质量问题/潜在 bug                   │
│  ├─ 异常处理策略                                  │
│  └─ 输出 TL;DR 摘要，等用户 "继续" 或提出修改       │
│                                                  │
│  🔴 红灯级（Agent 分析 + 方案对比 + 强制等待确认）    │
│  ├─ 新增依赖/库（需说明理由和替代方案）              │
│  ├─ 数据库表结构变更（DDL）                        │
│  ├─ 架构层次变动（新增模块/改变分层）               │
│  ├─ 安全相关决策（认证/授权/数据脱敏）               │
│  ├─ 部署/上线操作                                 │
│  ├─ API 接口签名变更（破坏性）                      │
│  └─ 输出详细对比分析，强制等待用户明确回复           │
└─────────────────────────────────────────────────┘
```

### 决策树（Agent 内部判断逻辑）

```
遇到一个决策点
    │
    ├── 属于编码规范/风格/格式？ → 🟢 绿灯，自主决定
    │
    ├── 属于设计/策略选择？
    │   ├── 影响范围 ≤ 单个类？ → 🟡 黄灯，摘要确认
    │   └── 影响范围 > 单个类？ → 🔴 红灯，强制等待
    │
    ├── 属于新增/变更基础设施？
    │   └── 任何情况 → 🔴 红灯，强制等待
    │
    └── 不确定属于哪一级？ → 🔴🔴 默认红灯，宁可多问不要擅作主张
```

## 用户覆盖指令

用户随时可以用以下指令改变 Agent 行为，无需修改配置：

| 指令 | 效果 |
|------|------|
| "全自动" | 所有门禁绿灯，Agent 全权决策，事后给出完整摘要 |
| "每步确认" | 回到传统 Pipeline 模式，每个决策都暂停询问 |
| "这个阶段自动" | 当前阶段内所有决策绿灯 |
| "设计部分问我就行" | 仅黄灯暂停，其他自动 |

## Pipeline 各阶段的默认门禁映射

| 阶段 | 典型决策 | 默认级别 | 说明 |
|------|---------|---------|------|
| 需求分析 | 功能范围界定 | 🔴 红灯 | 改需求影响全局 |
| 需求分析 | 用户故事/验收标准格式 | 🟢 绿灯 | 格式问题 |
| 系统设计 | 技术选型 | 🔴 红灯 | 新增依赖 |
| 系统设计 | 数据库表设计 | 🔴 红灯 | DDL 变更 |
| 系统设计 | API 路径/参数设计 | 🟡 黄灯 | 影响接口契约 |
| 系统设计 | 类名/包结构 | 🟡 黄灯 | 影响组织方式 |
| 开发实施 | 代码生成（PO/DTO/VO） | 🟢 绿灯 | 模板化工作 |
| 开发实施 | 业务逻辑实现 | 🟡 黄灯 | 核心逻辑 |
| 开发实施 | 代码审查修复 | 🟢 绿灯 | 风格类自动修 |
| 测试 | 测试用例生成 | 🟢 绿灯 | 模板化工作 |
| 测试 | 覆盖率阈值不达标 | 🟡 黄灯 | 需决策是否补充 |
| 部署 | 任何操作 | 🔴 红灯 | 直接触碰生产环境 |

## 在 Agent prompt 中的表达

```markdown
## 确认门禁策略

### 原则
- 你能做好的、不影响全局的 → 直接做，事后告知
- 需要设计判断、但影响可控的 → 给摘要，等我确认
- 影响基础设施、安全、架构的 → 必须等我明确回复

### 决策树
//anchor 每次面临决策时，按以下逻辑判断：

1. 是否属于编码规范/格式/命名？ → 直接决定（绿灯）
2. 是否影响范围 ≤ 单个类且非基础设施？ → 摘要确认（黄灯）
3. 是否新增依赖/改表结构/改架构/安全相关？ → 强制等待（红灯）
4. 不确定？ → 默认红灯

### 用户覆盖指令
用户可随时说"全自动"/"每步确认"/"这个阶段自动"来临时改变行为。

### 每阶段结束的标准输出
阶段 X/N 完成：[阶段名称]
- 🟢 自主决策（N 项）：[简要列表]
- 🟡 等待确认（N 项）：[关键决策摘要，≤5 行]
- 🔴 强制等待（N 项）：[需要用户明确回复的问题]
→ 请回复 "继续" 进入下一阶段，或提出修改要求
```

## 与 java-sdlc-pipeline 的关系

| 调用方式 | 行为 |
|---------|------|
| 用户直接 `/skill java-sdlc-pipeline` | 使用 Skill 原规则，每阶段硬确认 |
| 用户 `@aik-dev-agent 开发XXX` | Agent 自主编排 spec-*，使用三级自主权 |
| Pipeline 被 Agent 内部调用 | 不推荐：Agent 应直接调 spec-* 协调者而非 Pipeline |

**设计意图**：`java-sdlc-pipeline` 是"手动挡"——给人用的、需要人把控每一步。Agent 是"自动挡"——在设定的权限范围内自动推进，只在关键节点刹车。
