## 第一部分：决策偏好（D1-D6）

### D1：方案选择倾向

```
场景：要实现一个功能，有两种方式：
  A. 简单直接实现当前需求，不提前做抽象
  B. 预留接口/扩展点，为未来可能的变化做准备

你默认倾向哪个？
```

**对 Agent 的影响**：决定生成代码的抽象层次、接口设计复杂度。

---

### D2：重构态度

```
场景：需要修改一段能工作但写得不好的旧代码：
  A. 只改当前需要改的部分，保持最小变更范围
  B. 既然要动这里，就顺手把整个模块重构到符合当前标准
  C. 先标记 TODO，等项目有专门的重构迭代时再统一处理

你默认倾向哪个？
```

**对 Agent 的影响**：决定 PR 变更范围、修改旧代码时的激进程度。

---

### D3：技术保守度

```
场景：一个新功能可以用项目已有技术实现，也可以引入一个新库做得更优雅：
  A. 用已有技术，哪怕代码多一点（保守）
  B. 评估新库的质量和维护状态后，可以考虑引入（审慎开放）
  C. 只要新库明显更好就引入，不纠结（开放）

你默认倾向哪个？
```

**对 Agent 的影响**：决定是否推荐新版本/新库/新框架。

---

### D4：抽象阈值

```
场景：同样的逻辑出现了 N 次，才会提取成公共方法/工具类？
  A. 第二次出现就提取（激进 DRY）
  B. 第三次出现才提取（中庸）
  C. 有明显重复且提取后显著减少代码时才提取（保守）

你的阈值是？
```

**对 Agent 的影响**：决定何时建议提取公共代码。

---

### D5：依赖态度

```
场景：需要一个工具功能（如字符串处理、文件操作）：
  A. 尽量用 JDK 自带或项目已有库，不引入新依赖
  B. 如果已有库（如 Hutool）已包含，直接用，不重复造轮子
  C. 找最专业的库来做这件事，即使需要加依赖

你默认倾向哪个？
```

**对 Agent 的影响**：决定引入第三方库的决策倾向。项目已有 Hutool、Commons 系列。

---

### D6：性能态度

```
场景：写一段业务代码时：
  A. 先保证正确和可读，性能问题等出现瓶颈再优化
  B. 关键路径（如数据库查询、循环）从一开始就注意性能
  C. 每一行都考虑性能，即使牺牲一点可读性

你默认倾向哪个？
```

**对 Agent 的影响**：决定 SQL 复杂度、代码优化程度。

## 第二部分：交互方式（I1-I4）

### I1：汇报风格

```
Agent 完成任务后向你汇报：
  A. 结论先行：先给 3-5 行摘要，细节你自己问再看
  B. 过程可见：展示完整推演过程，确保没有遗漏
  C. 分级展开：默认摘要，关键决策自动展开详情

你偏好哪种？
```

### I3：失败处理

```
Agent 执行过程中遇到错误（如生成的代码编译不过）：
  A. 立即报告，让你来决定怎么修
  B. 先尝试自行修复（最多 N 次），修不好再报告
  C. 分析原因并给你修复选项，等你选择

你偏好哪种？
```

### I4：补充建议

```
Agent 完成你要求的任务后：
  A. 严格只做要求的，不做任何额外的事
  B. 可以提 1 条优化/改进建议，明确标注"可选"
  C. 主动检查和优化所有相关内容，一起汇报

你偏好哪种？
```

## 分析的思考记录

### 为什么性格画像对 Agent 至关重要

一个只有"技术规范"的 Agent 和一个有"性格"的 Agent，面对同一个需求会给出完全不同的方案：

```
需求：实现一个用户导出 Excel 的功能

"纯规范 Agent" 的方案：
→ 用 Apache POI，生成 XSSFWorkbook，逐行写数据
→ 代码正确，但引入新依赖，写法偏底层

"aIk Agent" 的方案（假设用户偏好：少依赖 + Hutool）：
→ 先用 Hutool 的 ExcelUtil 试试，不够再用 POI
→ 如果有 hutool-poi 依赖直接用，不重复造轮子
→ 给用户标注："可用 Hutool 内置封装，无需加依赖"
```

这个差异不是能力问题，是**决策偏好**问题——而决策偏好正是"像不像你"的关键。

### 关于 I2（行动方式）的设计思路

I2 问题我们已经在 [03-confirmation-gates.md](./03-confirmation-gates.md) 中设计了三级自主权模型。这个模型的本质是：

- 把"问你"的成本和"做错"的风险做匹配
- 低风险高成本的事（格式/命名）→ Agent 自己做
- 高风险低成本的事（表结构/安全）→ 必须问你
- 中间地带 → 摘要式沟通

这和你的 `java-sdlc-pipeline` 的设计哲学一致（"关键节点需人工确认"），但更细粒度——不是在"阶段"层面卡，而是在"决策类型"层面卡。

### 价值观排序为什么重要

Agent 会经常面临"两难选择"：

```
场景：一个查询需要 JOIN 三张表
  选择 A：用 MyBatis XML 写一条复杂 SQL（1 次查询，性能好，但 SQL 难读）
  选择 B：用 LambdaQueryWrapper 分 3 次查，代码里组装（3 次查询，代码清晰，但性能差）
  
  如果你价值观：可读性 > 性能 → Agent 选 B
  如果你价值观：性能 > 可读性 → Agent 选 A
  如果你价值观：正确性 > 一切 → Agent 两个方案都给，问你要哪个
```

没有价值观排序，Agent 会在每一次冲突时随机选择——这就是为什么有时候它"不像你"。
